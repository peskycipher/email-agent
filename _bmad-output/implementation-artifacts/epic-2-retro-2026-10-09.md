### Lens findings (narrowed inline)

The skill normally invokes `bmad-review` for the code lenses; that step was *narrowed* and run inline here because the epic is a single already-triaged story whose story-level review triaged 22 findings. The built-in reviewer (errors, security) was run on the two highest-stakes files; the warnings it produced are recorded and refuted against the source, rather than treated as findings.

- **`M365AuthAdapter.ts` (errors lens)** raised an unhandled-error warning. The error paths the story triaged (`refresh` catch limited to `AUTH_REQUIRED`; `requestDeviceCode` failure surfaces as `DEVICE_CODE_REQUEST_FAILED`; polling branches `slow_down` / `expired_token` / `authorization_declined` covered) all throw typed `M365AuthError`s that propagate to the orchestrator or, in `authenticate`, fall through to the device-code flow exactly as intended. Source-check: every awaited operation in the file is either inside a `try` whose `catch` re-throws typed errors, or has a typed-error constructor on the next line. **Refuted by source; not a finding.**
- **`KeychainTokenStore.ts` (security lens)** raised a secret-exposure warning. The store imports no logger, writes nothing to stdout/stderr, and constructs `TokenStoreError` messages that name the account and the operation but never include the token material, the keychain password, or the passphrase (`grep -n "console\.|stdout|stderr|log\." src/adapters/token/KeychainTokenStore.ts` → empty). The error messages and the `ACCOUNT_NAME_PATTERN` rejection in `M365AuthAdapter.assertAccountName` were also spot-checked for token leakage. **Refuted by source; not a finding.**
- **`parseTokenSet` does not field-validate `TokenSet` shape** — the final `as TokenSet` cast in `src/adapters/token/KeychainTokenStore.ts:255` accepts corrupted-but-valid JSON with missing fields. The story's review (row 5) rejected this as low. The intermediate code path now does a `JSON.parse` in `try` plus a `typeof === "object" && !== null` guard (lines 244-253), so *structurally invalid* JSON is caught; only *shape-invalid* JSON (e.g. `accessToken: 42`) is not. **Disposition:** low; recorded as action item 3.

**Evidence the epic is accepted:** the story is `done` (`pending_stories: []`); the `KeychainTokenStore` is the production token backend for both M365 and Gmail; the `M365AuthAdapter` device-code flow is the working auth path for `email-classify --auth m365 --account <name|all>`; the two cross-epic concerns the epic itself deferred (malformed-YAML isolation, 401→refresh) are both resolved by `0caa9f3` and `M365Adapter.ts:144-189`; build / lint / the four help-and-error CLI paths all run end-to-end.

**Evidence it is *not* fully accepted:** one residual risk from the story's own review — the `offline_access` scope question — has been open since `c3fae11` and was never confirmed. The `M365_SCOPES` constant is still frozen to two scopes; on a real Entra tenant the silent-refresh round-trip is expected to fail with `invalid_grant`. That's not a code defect today; it is an unconfirmed invariant the AC carried into production. Action items 1 + 2 close that loop.

No intent-gap or bad-spec evidence surfaced during the retro itself; the original spec remains coherent against the as-built code (modulo the deferred manual smoke).

## Open questions

- **Add `offline_access`, or replace silent refresh with re-prompt-on-expire?** The current story's "silent refresh until the refresh token is revoked" line is the one in tension with the two-scope `M365_SCOPES`. If `offline_access` is added, the silent-refresh promise holds; if it isn't, a refreshed-token flow requires the user to re-auth, contradicting the AC. This is action item 1 restated as a binary choice for the human — and the only choice in this retro that materially changes the shipped code.
