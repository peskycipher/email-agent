### Spec-to-implementation reconciliation

- **A. `GMAIL_SCOPES` / `GMAIL_SCOPE_URIS` split is correct in production.** `src/adapters/gmail/GmailAuthAdapter.ts:8` (`scopes Story 3.1 freezes`), `:16` (`GMAIL_SCOPE_URIS = GMAIL_SCOPES.map(...)`), `:424` (the consent URL sends the URIs), `:474` (the stored `TokenSet.scopes` keeps the short names). The story's review high-severity finding #1 (consent URL was sending the bare names and Google's OAuth endpoint would have rejected with `invalid_scope`) is the only "high" the triage raised, and it is fixed. **Disposition:** clean.
- **B. `CONSENT_UNAVAILABLE` was added to the typed-error code set** to cover the loopback listener's bind failure and any unhandled rejection from the injected `authorize` seam (per Implementation Notes, `spec-3-1-…md:124-127`). The typed-error invariant the AC requires is preserved. The underlying reserve→rebind race that surfaces as that code (`deferred-work.md:61`) is *still* open — fixing it needs the `authorize(authUrl, redirectUri)` seam to own the server, which is a seam-signature decision, not a mechanical patch. **Disposition:** deferral kept; cost is a rare typed retry.
- **C. `GmailAuthAdapter` takes `tokenStore: TokenPort` (like the M365 adapter), not `implements TokenPort` as the spine's structural-seed comment says** (`_bmad-output/planning-artifacts/architecture/.../ARCHITECTURE-SPINE.md:199`). Deviation recorded in Design Notes; the spine comment is human-owned and the reconcile is a planning pass. `deferred-work.md:62`. **Disposition:** open; planning.
- **D. No OAuth `state`/PKCE on the loopback consent.** Both were rejected-low in the story review (`spec-3-1-…md:135-141`); the loopback is single-shot on `127.0.0.1` and the trade-off (CSRF/PKCE cost vs the threat model) was explicit. Not in `deferred-work.md` (not a defect to fix, just a deliberate non-feature). **Disposition:** known limit; no action.
