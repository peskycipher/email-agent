Each story generalized correctly in its own session; nobody could see the accumulating quadruplication. Disposition: **tracked for Epic 11's DI collapse** — already in `deferred-work.md` from the 5.3 review; Epic 11's planning notes must inherit it (action item 3).
- **F3 (architecture delta): clean.** No layering violation (tsc + oxlint AD-10 gates green at every story), no new dependency, no cycles. The structural-seam pattern (the orchestrator declares, the adapter satisfies structurally — `MessageFetchTarget`, `GmailHistoryTarget`, the state seams) is now used consistently three times. Two deliberate architectural growths worth recording, not defects: `StateFileOptions.provider` threads per-provider cursor namespacing through every state seam (decision EC2/2-A), and `src/orch/incremental.ts` is now provider-aware rather than provider-agnostic (the Gmail branch lives beside the m365 branch at `src/orch/incremental.ts:175`) — acceptable at two providers, worth re-checking when a third appears.
- **F4 (spec-to-implementation reconciliation — the epic's planning text is now stale and Epic 8 reads it):** epics.md's epic-5 requirements say state lives at `~/.config/email-classify/state/<accountName>.json` with "M365 persists `lastRunTimestamp` …; Gmail persists `lastHistoryId`". As built (both decisions frozen in spec-5-4): per-provider files `state/m365-<name>.json` / `state/gmail-<name>.json`; a Gmail cycle writes **both** keys; the legacy name is read back (m365 only) and never written again. A later session deriving Epic 8's resumability from epics.md would read the wrong file layout. Source: epics.md epic-5 requirement block vs spec-5-4's frozen Always. Disposition: **spec reconciliation, proposed** — action item 2 (planning artifacts are human-owned, so the edit awaits explicit authorization).
- **F5 (spec-to-implementation reconciliation — NFR3's progress contract is not implemented as written):** the epic context's UX section says "Backfill reports progress every 100 messages per account (processed / labeled / skipped / errors)". As built, `fetchAllMessages` emits one per-account line (`Fetched N messages.`, `src/orch/fetch.ts:83`) and `--cron` prints per-account cycle counts — no per-100 tick exists. Contributing cause: the pipeline discards DTOs (counts only), so a per-100 tick needs the fetch loop's shape changed. Disposition: **open question** — declare the per-account line as v1's progress report (reconcile the epic text), or implement the tick in Epic 8 (it owns progress/orchestration). Action item 4 records it; the verdict below counts it as an open item, not a story failure (no story's AC promised the tick).
