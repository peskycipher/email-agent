## Findings

### Aggregate views

- **A1 (6.1 ↔ 6.3 cross-story boundary): `buildPrompt`'s output contract is inapplicable to the default Jev path.** The system prompt instructs *"Return only valid JSON, with no prose and no code fences, in exactly this shape:"* + `{"labels":["<label>"]}` (`src/core/skill/prompt.ts:65-68`), and the few-shot examples answer with JSON (`renderFewShot`). The 6.3/6.4 live probes prove the real mechanism: Jev answers are typed `noul` probabilities read from named questions — the model never emits that JSON, and the instruction text rides along in every request's `state` as inapplicable contract. For OpenAI the framing is redundant-but-consistent (6.3's structured outputs enforce the shape mechanically). The provider-neutral lines (`"Every label you return must come from the taxonomy"`, precision-beats-recall, empty-is-valid) are the load-bearing half. **Disposition:** the provider-neutral/JSON-split needs the 6.1 frozen intent renegotiated (action item 1); nothing else depends on it today because the Jev adapter synthesises the label set itself.
- **A2 (spec-to-implementation, PRD): the PRD's recorded Jev assumption is confirmed false and still stands uncorrected.** `prd-email-agent-2025-01-15/prd.md:490` — *"Jev System1 accepts the prompt format and returns valid JSON without additional parsing"* — the assumption this epic falsified with live evidence (systemOne is typed-questions-only; extra request fields 400; `system1` not a model id). Human-owned planning doc; reconcile owed. **Disposition:** action item 2 (spec reconciliation, Loki).
